# Обоснование событийного подхода vs интеграция через Camel ESB и DWH

## Проблемы текущей интеграции (Camel + DWH)

1. Точечные синхронные связи N×N. ESB на Apache Camel соединяет системы маршрутами
   «каждый с каждым»: добавление нового направления (фарма, производитель электроники,
   новый регион) требует правки множества маршрутов и координации всех участников.
2. DWH как шина данных и хранилище бизнес-логики. SQL Server 2008 несёт значительную часть
   бизнес-логики; любое изменение логики одного направления затрагивает общее ядро.
   Отчёт строится часами: batch-трансформации над сотнями терабайт не успевают за бизнесом.
3. Хрупкость и каскадные отказы. Синхронный вызов через ESB: недоступность потребителя
   блокирует производителя; повторные вызовы и согласование состояния — ручные операции.
4. Единая точка масштабирования. Масштаб DWH ограничен вертикально (лицензия, железо);
   новые сценарии использования данных умножают число трансформаций и замедляют time-to-market.
5. Устаревший стек. SQL Server 2008 и PowerBuilder сняты с поддержки: риски ИБ,
   дефицит компетенций, невозможность развиваться.

## Что даёт переход на интеграцию через события

| Критерий | Camel ESB + DWH (as-is) | Событийная платформа (to-be) |
|----------|--------------------------|------------------------------|
| Связанность | Синхронная, точечная: производитель знает каждого потребителя | Временная и топологическая развязка: производитель публикует факт, потребители подписываются |
| Гибкость | Новый сценарий = правка маршрутов ESB и/или трансформаций DWH с регрессией на всех | Новый потребитель подключается подпиской на существующий топик — производитель не изменяется |
| Масштабируемость | Вертикальное масштабирование DWH; ESB — узкое место | Горизонтальное масштабирование Kafka/обработки по партициям; каждый домен масштабируется независимо (Data Mesh) |
| Скорость реакции | Batch-отчётность: часы на сложный отчёт | Near-real-time: потоковые витрины обновляются по мере поступления событий (минуты/секунды) |
| Отказоустойчивость | Каскадные отказы при недоступности потребителя | Персистентность событий в шине, DLQ + replay; потребитель догоняет поток после сбоя |
| Эволюция контрактов | Согласование изменений маршрутов и схем DWH между командами | Schema Registry + версионирование событий и contract testing: изменения безопасны и независимы |
| Подключение новых доменов | Недели/месяцы интеграционных работ через ESB и доработки DWH | Публикация/подписка на событийные контракты через ACL — дни (self-service платформы) |
| Владение данными | Централизованная команда DWH — бутылочное горлышко | Домены владеют своими дата-продуктами; центральная команда поддерживает только платформу |

## Преимущества для «Будущего 2.0» конкретно

1. Развитие направлений без изменения ядра. Кейс требует: каждое направление развивается
   отдельно при целостной картине по ключевым показателям. Событийная модель даёт именно это:
   финтех, клиники, ИИ публикуют факты своей жизни, а витрины и портал собирают целостную
   картину подписками — без внесения бизнес-логики направлений в общее хранилище.
2. Интеграция покупок и партнёров (фарма, электроника, новые регионы). Подключение —
   адаптер/ACL и событийный контракт (см. `events.md`, события 14). Не требуется перестройка
   DWH или новых маршрутов «каждый с каждым».
3. Портал самообслуживания и time-to-market отчётности. Потоковые витрины + семантический
   слой сокращают подготовку отчёта с часов до минут; конструктор отчётов снимает очередь
   задач к центральной команде.
4. Near-real-time для финтеха и ИИ. Риск-метрики портфеля, мониторинг моделей, загрузка
   клиник становятся доступны сразу по факту события — цель кейса «переход от batch к
   near-real-time за 3 года».
5. Управляемая миграция вместо big-bang. ACL-мосты поверх Camel/DWH позволяют переводить
   интеграции постепенно, сохраняя работоспособность легаси до полного переноса логики
   в домены (стратегия «мостов совместимости» из кейса).
6. Соответствие регуляторике. Чувствительные медицинские данные не путешествуют через
   общую шину/DWH: события несут только факты и ID, содержимое остаётся в закрытом контуре
   домена; аудит всех обращений — в IAM/портале.

## Цена событийного подхода и как она снижается

| Издержка | Митигция |
|----------|----------|
| Eventual consistency: метрики сходятся не мгновенно | SLA свежести в карточках дата-продуктов, отметки «данные на момент T», согласованные снимки периодов (риск A3 плана управления) |
| Сложность наблюдаемости распределённых потоков | correlation_id в конверте события, трейсинг, мониторинг lag/DLQ с первого дня пилота |
| Требования к культуре и компетенциям | Обучение, гильдии, CoE платформенной команды, роли DPO/Data Engineer (риски O1/O2) |
| Двойная эксплуатация на период миграции | План-график демонтажа мостов со stop-датами (риск T6), TCO-контроль (задание 5) |

## Вывод

Интеграция через Camel ESB и DWH исчерпала масштабируемость: она связывает направления
синхронными точечными маршрутами и концентрирует бизнес-логику в устаревшем монолитном
хранилище. Событийный подход (шина Kafka + Schema Registry + DLQ, доменные дата-продукты,
ACL к легаси) напрямую закрывает цели бизнеса: независимое развитие направлений, целостные
ключевые показатели, портал самообслуживания, near-real-time аналитика и подключение новых
доменов за дни, а не месяцы. Остаточные издержки управляются мерами плана управления рисками
(задание 3) и окупаются снижением TCO (задание 5).
